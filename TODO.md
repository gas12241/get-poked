## Phase 4 — Authentication

Phase 4 is Google OAuth + email/password + user profiles + tests — shipped as four small, reviewable slices in order: email/password auth, then password reset, then Google OAuth, then a profile page. **Phase 4 is now complete.** The guest-mode/claim-on-signup question for Quiz and Horoscope (deferred since decisions.md #061) was raised again once Phase 4 was underway, and deferred again — both features stay login-required with no guest path. Changing your own email and account deletion were deliberately left out of the profile page (see docs/decisions.md #070) and remain open for later if wanted.

- [x] Swapped Django's default username-based `auth.User` for a custom `core.User` model with email as the login identifier (`USERNAME_FIELD`), done now rather than later specifically so the next slice (Google OAuth) has one identity to resolve to by email instead of two different lookup keys — see docs/decisions.md #067 for the full reasoning and the local-dev-database-reset consequence. Email/password registration (`POST /api/v1/register/`) with required email verification (`is_verified`, not `is_active`, gates login) via a signed, time-limited link (`django.core.signing`, no new dependency, no token table) emailed on registration (`POST /api/v1/verify-email/`, `POST /api/v1/verify-email/resend/`, both throttled via DRF's `ScopedRateThrottle`); successful verification also logs the user in. Login (`POST /api/v1/token/`, existing endpoint, now email-based) rejects an unverified account with a specific message. Also fixed a real doc/implementation drift found along the way: `docs/api.md` had documented login/logout at a `/api/v1/auth/...` prefix that was never actually built (the real, tested endpoints are `/api/v1/token/...`, per decisions.md #010) — new endpoints follow the real flat convention, and the doc was corrected.
- [x] Frontend: `LoginPage`/`SignupPage`/`VerifyEmailPage` at `/login`/`/signup`/`/verify-email`, `Layout.tsx`'s nav now shows Log in/Sign up or Log out based on real auth state (new `useIsAuthenticated()` selector, replacing a duplicated inline check in `QuizPage`/`HoroscopePage`). `apiClient.ts` gained a readable `.message` derived from the backend's actual error body (previously always a generic "API error 400: Bad Request") plus `.body` for callers needing more (e.g. detecting the unverified-login case to offer a resend action), and a deduped, silent refresh-and-retry on any `401` — also called once on app mount so a page reload restores the session from the httpOnly refresh cookie instead of always starting logged out. The dev-only `window.__authStore` escape hatch (used all session to test Quiz/Horoscope before real login existed) is retired now that its purpose is fulfilled.
